Synara connects to Google’s Antigravity CLI through the `agy` executable. Antigravity owns its account session, models, permissions, tools, and conversation runtime; Synara supplies the task boundary, working environment, transcript, browser, terminal, diff, and Git workflow around it.

## Install

On macOS and Linux, use the official installer:

```bash
curl -fsSL https://antigravity.google/cli/install.sh | bash
```

On Windows PowerShell:

```powershell
irm https://antigravity.google/cli/install.ps1 | iex
```

The Unix installer normally places `agy` under `~/.local/bin`. Verify the executable from a fresh terminal:

```bash
agy --version
```

Synara needs Antigravity CLI 1.5.0 or newer, because it runs Antigravity through `agy acp`. Run `agy update` if the version is older.

## Authenticate

Start Antigravity in a normal terminal:

```bash
agy
```

Antigravity first checks the operating system’s secure keyring. If no valid session exists, it opens Google Sign-In in a browser. In an SSH or remote session, it can print an authorization URL and accept the resulting code in the terminal.

To remove stored credentials from an interactive Antigravity session, use:

```text
/logout
```

Synara does not copy or replace the credential profile stored by Antigravity.

Open **Settings → Usage** to see the account’s remaining quotas and reset times. Synara runs
Antigravity’s official quota report in the background using the selected account’s existing sign-in.

## Verify

From a clean test directory:

```bash
mkdir -p /tmp/agy-synara-check
cd /tmp/agy-synara-check
agy
```

Confirm that Antigravity starts without a keyring or sign-in error and can answer a harmless read-only request. Exit before making changes. This isolates installation and authentication problems from Synara.

## Capabilities in Synara

Synara runs Antigravity through `agy acp`, the Agent Client Protocol server built into the CLI. Antigravity sessions can expose:

- Model and thinking-level selection discovered from the installed runtime
- Streamed assistant and reasoning text, with command, file, search, fetch, and web-search activity shown as it runs
- Synara's own tools and every connected connector, such as Notion, attached to each new session
- Context-window usage reported by the runtime
- Attachments, including images, projected into the provider prompt
- Conversation continuity: Synara resumes the same Antigravity conversation after a restart
- [Multi-folder projects](/docs/features/multi-folder-projects): the primary folder stays the working directory, and each additional folder is passed through `agy acp --add-dir`
- Synara’s terminal, browser, diff, checkpoint, and Git delivery surfaces

Choose **Approval required** to review Antigravity's native permission requests in Synara.
**Full access** can grant a request once. Computer Use actions use Synara’s own approval cards.

On Windows, an Antigravity session launched from a WSL folder requires every additional project folder to be in that same WSL distribution. Native Windows and other-distribution folders are refused for that session.

When Antigravity sends a command to the background, the turn stays open until the command finishes and Antigravity reports on it. Dev servers and other long-running daemons do not hold the turn open. Stopping the turn also stops its background commands.

When the session reports Antigravity 1.5.0 or newer, use **Steer** to send a follow-up while the agent and its subagents continue working. Older or unidentified runtimes use the existing interrupt and queue controls. If Antigravity asks a question, choose an answer in the composer, including in Full access mode.

Subagent activity shows the role and prompt for each launch. Synara shows child details when the active Antigravity profile identifies which launch owns the child.

Antigravity keeps its own settings and conversation data. Changes to its permission mode, sandbox, model, hooks, or workspace trust can alter behavior even when the same task is opened through Synara.

## Updating

Antigravity includes a native update path and its installer can install or upgrade the CLI. Keep the installation directory writable by your user and restart Synara after the executable changes.

If an update is stuck, check Antigravity’s own updater status and lock files before reinstalling. Do not delete unrelated files from its configuration directory.

## Troubleshooting

### Antigravity is not detected

1. Run `agy --version` from a fresh terminal.
2. Confirm `~/.local/bin` or the Windows installation directory is on `PATH`.
3. Remove or correct an obsolete custom binary path in Synara.
4. Restart Synara after installation or shell-profile changes.

### Authentication repeatedly opens or fails

Launch `agy` directly. Check whether the operating-system keyring is unlocked and available to your user session. In SSH environments, complete the printed authorization flow rather than expecting a local browser to open remotely.

### Models are missing

Update Antigravity, confirm the account can see the expected models in the CLI, then refresh provider status in Synara. Availability can depend on the account and runtime release.

### Antigravity is reported as too old

Synara needs Antigravity CLI 1.5.0 or newer. Run `agy update`, confirm the new version with `agy --version`, then refresh provider status in Synara.

### Connector or Synara tools are missing

Connectors attach when a session starts. Start a new chat after connecting a service; existing sessions keep the tools they started with.

### Antigravity reports an updater lock

Follow Antigravity’s updater troubleshooting guidance. A stale updater lock, read-only install directory, or competing update process can prevent the runtime from refreshing.
