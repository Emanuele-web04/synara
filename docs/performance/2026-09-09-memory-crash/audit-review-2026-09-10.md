# Review of `audit-2026-09-10.md` against the current code

Independent re-check of every claim in the 2026-09-10 audit. Measurements were re-run, several through the real engine and repository layers on a file-backed database created by the production migrations, not only the isolated SQLite script. Temporary fixtures were deleted after use; no production code was changed by this review. The retention fix from the audit (`retainedTurnItems.ts` and its call sites) is still in the worktree and is assessed below, not endorsed.

## 2. Reproducible measurements

Runtime: node 26.8.1, SQLite 3.53 (node:sqlite), Apple M5 Pro / 48 GiB, macOS 25.6.0, `bun run test` (Vitest 4.1.10). Not the incident host, not the packaged Electron runtime.

Permanent rows per delta (8 KB case): 1 `orchestration_events` row (~235 B) and 1 `orchestration_command_receipts` row; neither is ever pruned except by thread purge (`profileStatsArchive.ts:794`). Modest, but unbounded per token chunk.

### 2b. Runtime journal per event (temporary fixture, deleted)

`ProviderRuntimeEventRepository.append` + `advanceConsumerCursor` for 1,000 `content.delta` events of 40 bytes: **27,246 bytes of WAL per event**, 0.105 ms per event (`journal-writes-1000-40.json`). This is paid before ingestion for every runtime event of every provider, independent of message size.

### 2c. Isolated SQLite script (`streaming-delta-writes.mjs`)

Kept as the lower bound; it under-reports the engine path by 1.3–3.2x because it has no receipts, indexes or journal.

### 2d. Turn-mirror retention (`retained-turn-items.mjs`)

200 turns × 4 items, forced GC, three runs: 64 KiB items 50.25 → 0.36 MiB; 2 KiB items 1.82 → 0.12 MiB. Retained heap for that collection only; not RSS, not adapter memory, not SDK memory.

## 4. Defects and regressions (with references)

1. **Streaming write amplification** (unfixed, confirmed): `ProjectionPipeline.ts` hot path; O(length²/chunk) WAL per message; 27 KB more per event in the journal. Highest-priority backend defect.
2. **Turn-item release mutates returned snapshots** (introduced by the audit's fix): `CursorAdapter.ts:1554`, `GrokAdapter.ts:2135/2150`, `DroidAdapter.ts:1823`, `DevinAdapter.ts:3075` return `turns: ctx.turns` by reference from `readThread`/`rollbackThread`; `releaseAllButLatestTurnItems` empties those arrays in place and casts away the contract's `ReadonlyArray` (`retainedTurnItems.ts`). A holder of an earlier snapshot observes its items vanish. No production holder exists today; the contract (`ProviderThreadSnapshot`, "Read a provider thread snapshot") does not say items may be dropped.
3. **`readThread` history change** (introduced): earlier turns now report `items: []`. Resume cursors (`turns.length`), Pi rollback (`leafId`) and Cursor/Grok rollback (`splice`) are unaffected; Pi's `readThread` fallback path (`snapshotThread` when SDK history is empty and no turn is active) now returns empty older turns. `importThreadRoute` only reads Codex/OpenCode snapshots. This is a policy change that needs an explicit contract, not an incidental one.
4. **Orphaned processes on unclean backend exit**: confirmed for OpenCode (`opencodeRuntime.ts:916`, `detached: false`, HTTP server survives EOF) and Cursor (`cursor-agent acp` survives EOF); Pi shells (`ownProcessGroup: true`) survive by construction. Codex and Claude exit on stdin EOF in the idle state. No ledger or group kill exists anywhere.
5. **Uncompacted events fan out to five subscribers** (`ProviderService.ts:1324`); the only byte bounds are adapter transports. Under a SQLite stall this is where memory accumulates first.
6. **OpenCode session-lifetime part retention** (unchanged): `OpenCodeAdapter.ts:381-382` and `2262-2266` store each `Part` plus its JSON key until the session stops.
7. **Idle retry without backoff** (local change): `ProviderService.ts` retries a failed idle teardown every ≤30 s, each running a synchronous `ps -eo` (`processTreeController.ts:131`).

## 6. Prioritized fixes and the tests that establish safety

1. **O(delta) streaming writes** (delta rows, materialize at completion). Safety tests: existing `OrchestrationEngine` Unicode/segment test; a new replay-idempotence test (apply the same delta events twice, assert identical text and segments); a reader-equivalence test that snapshots, exports and `getByThreadAndMessageId` return identical text before and after the migration for streaming and completed messages; the engine-level WAL benchmark above rerun (expect WAL ≈ message size + row overhead per message).
2. **Batch journal cursor advances per drained page** (one transaction per page, keep the contiguity check). Safety tests: crash between page processing and advance replays only unacked rows; `ProviderRuntimeEvents.test.ts` retention sweep still fires on terminal events.
3. **Process ledger + group ownership** for OpenCode, Cursor/Grok/Droid/Devin and Pi shells first (the ones shown or built to survive). Safety tests: fixture tree (root + grandchild) killed via the ledger after simulated owner death; PID-reuse guard with a different start time; graceful stop still proves exit through the existing teardown.
4. **Turn-item mirrors**: replace in-place mutation with a documented contract. Either (a) drop `items` from `ProviderThreadSnapshot` for the four ACP adapters and Claude and make `readThread` return a copied, explicitly bounded snapshot, or (b) keep the latest-turn policy but replace turn records (`turns[i] = { ...turn, items: [] }`) and copy on read, so earlier snapshots are immutable. Safety tests: snapshot taken after turn 1 is unchanged after turn 2; contract test in `providerAdapterConformance.test.ts` that `readThread` results are not aliased to adapter state.
5. **Compact before fan-out**: publish the journal-compacted event (or apply `shrinkRuntimeEventStrings` once) to the PubSub so the five subscribers share a bounded object. Safety test: reactors that read `payload.detail`/`raw` (CheckpointReactor, StudioOutputReactor) keep working with the 64 KiB leaf cap.
6. **OpenCode settled-part eviction** and **idle retry backoff**, as described in the audit.

## 7. Corrected conclusion

What is proven: the streaming projection write path is quadratic per message and, measured through the real engine and migrations, writes 15 MiB for an 8 KB message and 1.3 GiB for a 200 KB message in 40-byte chunks, on the backend's event loop; every runtime event adds a further ~27 KB; checkpoints add 4–13 %, not 100 %. Two of four tested provider CLIs (OpenCode, Cursor) outlive an unclean backend exit, Pi shells are built to, and nothing records or reaps them. Six adapters retained per-turn raw items for the life of a session; the applied release is effective for that collection but aliases and mutates snapshots returned by four adapters and needs a contract decision before it ships.

What is not proven: that the write path alone produced the incident's disk totals or the panic; what the two 4 GB `node` processes were (Cursor sessions and MCP servers are `node`; Claude, Codex and OpenCode are not); that any provider is free of unbounded growth; and any whole-app RAM effect of the changes in this worktree. No claim of "leak-free", "all providers safe", or "crash fixed" is supported by this evidence.

## 8. Review of the implementation landed after this review (`implementation-2026-09-10.md`)

Checked against the code, with the affected suites re-run (82 files, 1,119 tests passed, 1 skipped; `bun typecheck` passed) and the WAL fixture re-run with per-table frame attribution via `dbstat` (`review-chunk-pages-*.json`).

**Confirmed.** `message_text_chunks` (migration 100) removes the growing-row rewrite: per delta the engine now writes a fixed ~19 WAL frames (77–82 KB) regardless of message size. 8 KB → 14.75 MiB (was 15.2), 50 KB → 97.5 MiB (was 154); the reported 200 KB → 402 MiB is consistent with 78 KB × 5,000. Readers (repository, snapshot, export, engine completion path) assemble text from chunks; `profileStats*` only read user messages and are unaffected. Replay watermark (`text_event_sequence`), rollback watermark, legacy prefix chunk, FK cascade on purge and surrogate handling are covered by tests. The `readThread` aliasing defect (§4.2) is fixed by copy-on-read (`snapshotProviderTurns.ts`); the latest-turn release was removed, so the six-adapter session-scoped retention (§4, F3) is again unbounded and is stated as such. OpenCode keeps SHA-256 fingerprints instead of JSON copies (≈50 MiB → 0.14 MiB for that collection at 3× the hashing cost).

**What remains, measured.** The per-delta floor is now the whole cost and it is unchanged for typical messages (8 KB: −2.4 %). Frames per delta by b-tree (8 KB run): `projection_state` 2.0 (a second transaction per committed event, `projectDeferredEvent` in `OrchestrationEngine.ts:942`, even when no deferred projector consumes the event), `orchestration_events` + 4 indexes ≈ 5.2, `orchestration_command_receipts` + 3 indexes ≈ 4.0, `projection_thread_messages` row + 3 indexes 4.0 (the per-delta upsert sets `role`/`source`/`created_at`-indexed columns even when unchanged, so SQLite rewrites all three index pages), `message_text_chunks` + index 2.3, `sqlite_sequence` 1.0. Two engine commits plus two journal commits (27 KB) per token chunk ≈ 105 KB and 4 transactions per delta.

**Next fixes, in order of bytes saved per delta.** (1) Skip or batch the deferred-projection transaction for event types no deferred projector handles (−2 frames, −1 commit). (2) Replace the per-delta message-row upsert with an `UPDATE` that sets only `updated_at`, `is_streaming` and `text_event_sequence` (−3 index frames). (3) Batch journal cursor advances per drained page (−1 commit, most of the 27 KB). (4) Longer term, carry delta idempotency on the chunk watermark so delta commands do not need a receipt row (−4 frames). Safety tests for each: replay the same event twice and assert identical text/segments; crash between commit and deferred pass replays from `projection_state`; existing `messageTextChunks.test.ts` and `OrchestrationEngine.test.ts` suites.

**Minor.** `settle` deletes chunks that `upsert` already deleted (harmless). `json_group_array(... ORDER BY ...)` needs SQLite ≥ 3.44; the packaged Electron/Node runtime should be checked once. `overlayThread` now replaces cached messages with durable detail (2,000-message cap) for rollback/edit deciders; covered by the new restart test.
