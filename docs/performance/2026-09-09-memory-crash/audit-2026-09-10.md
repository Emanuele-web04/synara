# Independent audit: memory, disk writes, and process cleanup (2026-09-10)

> Reviewed on 2026-09-10 in [audit-review-2026-09-10.md](audit-review-2026-09-10.md). That review corrects several statements here: physical writes are ~1.04–1.13× WAL, not 2×; the 512 KiB/2 MiB compaction does not bound the PubSub fan-out; Codex and Claude exit on parent death while OpenCode and Cursor do not; Pi shells run in their own process group; and the turn-item release aliases snapshots returned by four adapters. Read the review before acting on this file.

Second-pass audit of the current worktree (HEAD `71862f9b2` plus local changes) against the 2026-09-10 kernel-panic report. Every claim in the report and in the earlier local reports was re-derived from the code. No incident-host process was inspected or killed; no user database was touched; nothing was committed.

## Verdict

- The report's "Synara main process writes 34–137 GB/day through synchronous SQLite" is **explained by a confirmed defect in the projection write path**: every streamed assistant token chunk rewrites the whole accumulated message row twice (`projection_thread_messages.text = text || ?` and `message_text_segments.text = text || ?`), inside one synchronous transaction on the backend event loop. Measured with the real `node:sqlite` in WAL mode: one 200 KB message streamed in 40-byte chunks writes **1.06 GB** of WAL; a 400 KB message writes **4.0 GB**. This is O(n²) per message and is not fixed by the local changes. The complete fix is a schema change (delta rows), described below; it was not applied here.
- The two 4 GB `node` processes cannot be attributed from the code alone. Synara has **no persisted ledger of provider child PIDs**, so a backend that crashes or is SIGKILLed (the report lists five `node` SIGABRTs on Sep 9 and repeated backend restarts) leaves every provider tree alive with nothing that will ever reap it. This is the most plausible source of large idle `node` processes that survive across Synara restarts, and it is unfixed.
- The local changes are sound and were verified; two regressions in them are noted (§4). They remove real retention (OpenCode turn mirror, Pi cumulative tool snapshots, dock terminals) but they do not touch the two items above.
- This pass fixed one further confirmed retention defect present in six adapters (Claude, Cursor, Grok, Droid, Devin, Pi): per-turn raw item mirrors kept for the life of the session with no consumer. Retained heap in a 200-turn simulation went from 50.25 MiB to 0.36 MiB.

## 1. Method

1. Registry verified: `ProviderAdapterRegistryLive` binds exactly nine adapters (Codex, Claude, Cursor, Devin, Antigravity, Grok, Droid, OpenCode, Pi).
2. Traced the shared pipeline end to end: adapter queue → `ProviderService` pump → runtime journal (`provider_runtime_events`) → PubSub → `ProviderRuntimeIngestion` (journal cursor consumer) → `OrchestrationEngine` transaction (event append + hot projection + receipt) → PubSub → WebSocket sliding buffers.
3. Enumerated every `Queue`/`PubSub`/`Stream.async` construction site and every session-scoped `Map`/`Set`/array in all nine adapters, then traced actual consumers of each retained collection before proposing removal.
4. Reproduced the write amplification with the real SQLite driver, and the retention defect with adapter-level regressions that fail on the pre-fix source.

## 2. Findings, prioritized

### F1 (critical, unfixed): quadratic streaming writes on the backend event loop

`apps/server/src/orchestration/Layers/ProjectionPipeline.ts` (`appendStreamingThreadMessageText`, `appendCurrentMessageTextSegment`) rewrites both growing rows on every `thread.message-sent` streaming delta. `ProviderRuntimeIngestion` dispatches one such command per provider `content.delta` when delivery mode is `streaming` (the default, `DEFAULT_ASSISTANT_DELIVERY_MODE`). Each dispatch is one synchronous transaction in `OrchestrationEngine.processEnvelope` that also inserts the event row and the command receipt. SQLite rewrites the whole record and its overflow chain on each UPDATE, so bytes written per message grow with (length² / chunk size).

Measured (`streaming-delta-writes.mjs`, node 26.8.1, SQLite WAL, `synchronous=NORMAL`, autocheckpoint disabled so the WAL size is the exact write volume; fresh process per row):

| Message | Chunk | Updates |  WAL written | Amplification | ms / delta |
| ------: | ----: | ------: | -----------: | ------------: | ---------: |
|    8 KB |  40 B |     200 |     4.81 MiB |          630x |      0.038 |
|   30 KB |  40 B |     750 |    35.92 MiB |        1,256x |      0.066 |
|   50 KB |  40 B |   1,250 |    84.29 MiB |        1,768x |      0.082 |
|  200 KB |  40 B |   5,000 | 1,059.27 MiB |        5,554x |      0.236 |
|  200 KB | 200 B |   1,000 |   212.20 MiB |        1,113x |      0.240 |
|  400 KB |  40 B |  10,000 | 4,039.66 MiB |       10,590x |      0.438 |

Checkpointing then copies the same pages into the main database, so physical writes are roughly double the WAL figure. Twenty agents each producing a few dozen 8–30 KB messages per hour is enough for the daily 34–137 GB in the report, and the per-delta cost is paid on the same thread that serves every WebSocket client. This matches the `StatementSync::All → pwrite` stacks: `all()` is what the sql client runs for UPDATE statements too.

Why it was not fixed here: the text column is read directly by seven modules (`ProjectionSnapshotQuery`, `ProjectionThreadMessages`, `ProjectionPipeline`, `projector.ts`, `profileStats.ts`, `profileStatsArchive.ts`, `threadDiagnosticTools.ts`). Coalescing deltas before the journal was evaluated and rejected: at real token rates (roughly 200–400 B/s for Claude) a 100 ms window merges only 1–3 chunks, so it buys 2–5x while changing event granularity and replay semantics. The renderer already coalesces on its side (`apps/web/src/orchestrationEventCoalescing.ts`).

Concrete safe fix (schema change, O(delta) writes, no history loss):

1. Add `message_text_deltas(thread_id, message_id, segment_sequence, sequence INTEGER, text, created_at, PRIMARY KEY(thread_id, message_id, sequence))`. The streaming hot path inserts one row per delta (`INSERT OR IGNORE` keyed by the event sequence, so journal replay stays idempotent) and only bumps `updated_at`/`is_streaming` on the message row. No growing row is rewritten.
2. Completion (`streaming: false`) materializes once: `text` = existing text || group_concat(deltas ORDER BY sequence), rebuilds `message_text_segments` from the deltas grouped by `segment_sequence` (same rows the UI sees today), and deletes the delta rows.
3. Reads of a message with `is_streaming = 1` use a view or a small helper that appends `group_concat` of its delta rows; only the seven readers above change, all through one shared query fragment. Export/snapshot windows already join segments per selected message, so the extra join is bounded by the display window.
4. Migration: no backfill needed; existing streaming rows keep working because the helper falls back to `text` when no delta rows exist.

Verification for that change: rerun `streaming-delta-writes.mjs` against the new pipeline shape (expect WAL ≈ message size + row overhead), then measure event-loop delay under a 20-thread streaming load in the packaged build.

### F2 (critical, unfixed): provider trees are orphaned whenever the backend dies unclean

- Provider children are spawned in the backend's own process group with no `detached`/`setsid` (`platform/effectProcessRuntime.ts`, `codexAppServerManager.ts`, Pi's shell supervisor, Antigravity, the Claude SDK spawn). Teardown captures descendants via `ps -eo pid,ppid` **while the root is alive** (`platform/processTreeController.ts`, `supervisedProcessTeardown.ts`), which is correct for graceful stop.
- Nothing records `{pid, start time, command}` durably. `persistence/Layers/ProviderSessionRuntime.ts` and `ProviderSessionDirectory` store no PID. Startup only heals _turn state_ ("Heal turns orphaned by the previous process exit", `effectServer.ts:216`); it never signals leftover processes.
- The desktop stops the backend with HTTP shutdown → SIGTERM → SIGKILL (`apps/desktop/src/main.ts`, `stopBackendAndWaitForExit`) and signals only the backend PID; there is no process-group kill in `apps/desktop/src`. A SIGKILLed or crashed backend (OOM abort, the Sep 9 `SIGABRT` cluster, supervision restarts) therefore leaves every provider CLI, MCP server, and shell running, holding their heaps, invisible to the new backend.
- Post-exit `ps` snapshots cannot recover this: reparented children have `ppid = 1`.

Concrete safe fix:

1. Spawn every provider root in its own process group (`detached: true` on POSIX, without `unref`, so the backend still supervises it). Record `{pid, pgid, startTicks/`ps -o lstart`, argv[0], provider, threadId, backendInstanceId}` in a small SQLite table (`owned_processes`) or a JSON ledger under the state dir, written before the first byte is sent to the child and removed only after `teardownProviderProcessTree` proves exit.
2. On startup (and in the desktop's crash-restart path), read the ledger, verify identity (pid alive, same start time and command), then `kill(-pgid, SIGTERM)` → SIGKILL with the existing grace timings, and only then delete the row. Identity checks make PID reuse safe.
3. Keep the existing PPID capture for graceful stops; the group kill is the backstop for descendants that already reparented.
4. Regression: spawn a fixture tree (root + grandchild), kill the owner without teardown, restart the reaper against the ledger, assert both are gone and that a reused PID with a different start time is not signalled.

### F3 (high, fixed here): unbounded per-turn raw item mirrors in six adapters

Claude appended every raw SDK `message.message` (assistant blocks, `tool_result` bodies, image blocks) to `context.turns[i].items` for every turn of the session (`ClaudeAdapter.ts` handleUserMessage/handleAssistantMessage → `context.turns.push` at completion). Cursor, Grok, Droid and Devin pushed `{prompt: promptParts, result}` per turn, where `promptParts` carries user image data. Pi kept one snapshot per tool call (after the local fix) with full output and result for every turn.

Consumer trace: `readThread` is called in production only for Codex and OpenCode (`orchestration/importThreadRoute.ts`); no code reads older turns from these mirrors. `turns.length`/ids are used for resume cursors and rollback; Pi's `readThread` already serves history from the SDK session and only exposes the active turn's items. Durable history lives in the projection and each provider's own transcript.

Fix: `apps/server/src/provider/retainedTurnItems.ts` releases the items (and Pi's tool indexes) of every turn except the latest one after each turn record is appended; turn ids and rollback leaves are untouched. Applied at all 16 push sites across the six adapters. This is a bounded policy (latest turn), not a count cap, and it is stated in the module header.

Measured (`retained-turn-items.mjs`, 200 turns × 4 items × 64 KiB random strings, forced GC): retained heap **50.25 MiB → 0.36 MiB**, retained items 800 → 4. Isolated mechanism probe, not whole-adapter RSS.

Regressions: `ClaudeAdapter.test.ts` ("releases raw SDK items of earlier turns once a newer turn completes") and `DevinAdapter.test.ts` ("keeps only the latest turn's prompt mirror once a newer turn settles"). Both were run with the helper call disabled and failed (`expected [ { …(2) } ] to deeply equal []`), then passed with it restored. `retainedTurnItems.test.ts` covers the helper. Cursor/Grok/Droid use the identical ACP push pattern and their suites pass; they have no direct readThread assertion.

### F4 (medium, unfixed): OpenCode retains full history parts twice

`OpenCodeAdapter.ts` `rememberOpenCodeMessageSnapshot` (session start/resume) and every `message.part.updated` store the full `Part` in `partById` **and** its `JSON.stringify` in `partSnapshotKeyById`, plus `emittedTextByPartId`, for every message of the session. The local `openCodeMessageState.ts` releases parts on `message.removed`/`part.removed` and at turn end for related child sessions, which is correct, but completed parts of the session's own messages live until the session stops. Tool outputs are therefore held twice for the session lifetime.

Why it is not a one-line eviction: `partById` is the dedup source for late `message.updated` fan-outs (line ~2173 iterates all parts of a message) and `emittedTextByPartId` decides what text has already been streamed. Evicting a completed message's parts and later receiving an update for one of them would re-emit its whole text as a delta into whatever turn is active.

Safe approach: on turn completion, move the ids of that turn's settled parts into a bounded `settledPartIds` set and drop their bodies and JSON keys; in `emitAssistantTextDelta`/`message.updated` skip parts whose id is settled (log once). Replace `partSnapshotKeyById` with a cheap content hash (or `part.time.end`/state comparison) so the serialized duplicate disappears entirely. Regression: stream a 64 KiB tool part to completion, complete the turn, replay the same `message.part.updated`, assert no new runtime event and that only the settled id remains.

### F5 (medium, unfixed): journal and cursor cost per event

Every provider runtime event is one journal INSERT transaction (`ProviderRuntimeEvents.append`, up to 2 MiB after compaction) plus one cursor UPDATE transaction (`advanceConsumerCursor`), before the delta reaches the projection. That is three WAL transactions per token chunk. This is the fixed-cost floor visible in the 8 KB row above (≈25 KB written per delta before the quadratic term). Batching cursor advances per drained page (one transaction per `PROVIDER_RUNTIME_REPLAY_PAGE_SIZE` page, preserving the contiguity check) removes one of the three without changing durability; the journal insert itself is the price of the crash-replay design and should stay.

### F6 (medium, partly by design): count-bounded stages

| Stage                                                                           | Bound                                     | Bytes bounded?                      |
| ------------------------------------------------------------------------------- | ----------------------------------------- | ----------------------------------- |
| Adapter callback ingress (Codex, Pi, Antigravity)                               | 2,048 events                              | yes, 32 MiB, terminal reserve       |
| ACP notification dispatcher (new, local)                                        | 2,048 / 32 MiB                            | yes; overflow closes the connection |
| Adapter event queues (Claude, Codex, Pi, Antigravity, OpenCode) and ACP PubSubs | 2,048                                     | no                                  |
| `ProviderService` runtime PubSub                                                | 2,048                                     | no                                  |
| `ProviderRuntimeIngestion` worker                                               | 1,024                                     | no                                  |
| Engine command queues / event PubSub                                            | 256 / 1,024                               | no                                  |
| WebSocket live streams                                                          | 1,024 sliding, drops oldest               | no                                  |
| `ProviderCommandReactor` live queue                                             | unbounded (deliberate, engine detachment) | no                                  |

Runtime events are compacted to 512 KiB before the callback ingress and to 2 MiB before the journal, so a full 2,048-slot stage can still hold up to 1 GiB in the worst case; in practice payloads are far smaller. The unbounded reactor queue is fed from a bounded PubSub and drained by a serial consumer whose only slow step is SQLite; if F1 stalls the loop, this queue is where events accumulate. Byte accounting on this queue (log + backpressure to the PubSub above a byte budget, never dropping) is the right instrumentation before choosing limits.

### F7 (low): idle retirement paths

- Idle stop requires a resume cursor (`hasResumeCursor` in `stopIdleRuntimeSession`); sessions without one are never idle-stopped, only reaped by `ProviderSessionReaper` after 30 minutes of inactivity. Acceptable, but worth a log line.
- The local retry loop retries a failed idle teardown every 1–30 s forever while the generation stays current, running a synchronous `ps -eo` each time. Add exponential backoff to the 10-minute idle interval after a few attempts.
- `processTreeController.ts` shells out to `ps` synchronously on the event loop; with 550+ host processes this is tens of milliseconds per teardown poll (250 ms interval).

## 4. Review of the local changes

All 28 modified and 5 new files were read. Verdicts:

- **ProjectionSnapshotQuery**: rank-then-join is correct; joins use the PKs (`(thread_id, message_id)`, `activity_id`). The segment join by `json_each` is bounded by the selected window. Kept.
- **ProviderService** idle retry: correct; every adapter's `stopSession` is a no-op for unknown threads (checked all nine), so the unconditional `adapter.stopSession` cannot loop on "not found". See F7 for backoff.
- **boundedCallbackIngress** finalizer `stop → abort`: all three users (Codex, Pi, Antigravity) create the ingress at layer scope, so aborting only discards events during whole-layer teardown. Correct, but note that a `turn.completed` queued at shutdown is dropped and relies on startup turn reconciliation.
- **AcpNotificationDispatcher**: bounds the SDK's non-awaiting receive loop; overflow closes the connection rather than dropping silently. Two costs: `JSON.stringify` of every notification on the hot path (transient copy of large tool outputs), and a full transport failure instead of backpressure once 2,048 notifications or 32 MiB are pending behind a stalled SQLite loop. With F1 unfixed, that stall is the realistic trigger.
- **OpenCode message state**: correct routing of removals; does not address F4.
- **Pi** one-snapshot-per-call: correct; F3 now releases it per turn.
- **Claude** failed-startup owner retention and **ThreadDeletionReactor/terminal scope** changes: correct; terminal shutdown waits for SIGKILL escalation (`disposeForShutdown`).
- **Renderer** terminal runtime pruning: exact scope matching, lazy registration, correct ordering after buffered newer events.

## 5. Measurements and limits

- `streaming-delta-writes.mjs` / `.json`: exact WAL bytes for the two `text || ?` UPDATEs plus the event insert per delta, one message, fresh process per row. Excludes receipts, cursor transactions, checkpoints, and page-cache effects; therefore a lower bound on physical writes.
- `retained-turn-items.mjs` / `.json`: retained heap after forced GC for the mirror pattern with and without the release helper. Excludes adapter, SDK and queue memory.
- Both ran on the development host (48 GiB, node 26.8.1), not on the 16 GiB incident host or the packaged Electron runtime. No whole-app RSS, crash-frequency or daily-write percentage is claimed.
